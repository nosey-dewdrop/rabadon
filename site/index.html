rabadon is an agent aid. Guardrails and a verifiable record for coding agents.

run your coding agent without sitting there watching it.

It refuses the destructive command before the process starts, writes a receipt you can verify afterwards, and when a check goes red it repairs the code without being able to buy its own green.

On this machine it has refused 207 commands, and it has found 31 real defects in express, lodash, ajv, commander, click, jinja, markupsafe and pyyaml.

run it

Five commands. It starts in watch mode and stays there until you say otherwise, because a tool that blocks your work on the first day is a tool you delete on the second.

$ git clone https://github.com/nosey-dewdrop/rabadon && cd rabadon && make rabadon watch record what it would have refused, block nothing rabadon on arm the gate. off, and the binary stops acting rabadon usage what was refused, what passed, what the session cost rabadon repair --cmd "npm test" catch a red check, hold a fix only if the proof survives rabadon audit verify the ledger chain back to the first line written

A dependency-free C++ core. Nothing is uploaded, nothing calls home, and the ledger is a file on your own disk.

A law written into a prompt is a request, and the model can drift off it or be argued out of it. rabadon sits underneath, compiled into the path every command takes, so refusing costs the agent the execution rather than an apology.

the gate, on the cases it was built against

Thirty-four cases lifted out of real sessions, eleven of them genuinely destructive, and the gate refuses all eleven and nothing else. Printed as it came, on this machine.

The eleven are not hypotheticals. They are commands that were typed during real work, by an agent, in a repository that mattered.

The other twenty-three are the harder half. Every one of them looks dangerous and is not, and a gate that refuses those is a gate you turn off in a week. That is why the floor was recall, and why precision had to climb to meet it rather than the other way around.

Nothing in the fixture was written for the fixture. It was lifted out of sessions that had already happened.

the laws are compiled in, not configured

A guard that lives in a config file is a guard the agent can edit. These live in the binary, and the parser that reads the command is the same one the laws are written against, so a new spelling of an old danger does not open a door.

outside the treeA delete is judged as a resolved path, never as text. A glob, a symlink, a temp directory pointing home, a .. walking back out, an environment variable set by the caller: all of it resolves first and is judged after.
history already sharedRewriting a branch that exists on a remote destroys work that is not yours. The gate refuses it and names the branch and the remote it would have overwritten.
data becoming programA dangerous string quoted as an argument is inert, until the next process reads its program from standard input. Both classifications were correct on their own, which is why the check has to live where the two meet.

Every law that blocks something carries a case it must let through, on the same line. A rule that only ever says no is a rule nobody keeps switched on.

a repair is accepted only when the proof could not be bought

When a check goes red, rabadon proposes a fix in an isolated copy and then judges it. The judge is the project's own test suite, and the cheapest way to cheat a test suite is to change it. So the suite is hash-locked before the proposer starts, and so is the machinery that decides which tests run at all.

a proposal that neutered the test

gate fix-add failed, repairing (1/1) FAIL testsuite [python3 test_calc.py] the project's own suite is RED FAIL forbidden [test_calc.py] protected content was modified STOP, fix-add cannot pass loop exit code 1 fail-closed

a proposal that touched only the source

gate fix-add failed, repairing (1/1) FAIL testsuite [python3 test_calc.py] the project's own suite is RED PASS accept: the output is the one that was asked for the patch is HELD, never applied loop exit code 0 accepted

Locking the test files is only half of it. A proposal can leave every test byte-identical and still buy its green by moving the harness that chooses which tests run, so the harness is locked too, and a file appearing where none existed counts as a change.

The same six cases against the previous binary come back three pass and three fail, and all three failures are the product printing VERIFIED over a fix that repaired nothing. Both honest repairs still certify, because a lock that refuses real work is not a lock, it is an outage.
